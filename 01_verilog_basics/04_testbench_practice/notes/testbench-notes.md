# Testbench Notes

## Topic

Testbench practice and verification-oriented simulation

## What is a Testbench?

Testbench

A testbench is a simulation environment used to verify whether a Verilog module works correctly.

It is not the hardware design itself.

The hardware design is the module being tested. The testbench provides inputs, observes outputs, compares actual results with expected results, and generates waveform files for debugging.

## DUT

DUT

DUT means Device Under Test.

It is the Verilog module being tested by the testbench.

In today's practice, the DUTs include:

* `mux2to1`
* `decoder2to4`
* `full_adder`
* `alu_4bit`

Example:

```verilog
alu_4bit dut (
    .a(a),
    .b(b),
    .opcode(opcode),
    .result(result),
    .zero(zero)
);
```

The `alu_4bit` module is the DUT.

The testbench is only the environment around the DUT.

## Stimulus

Stimulus

Stimulus means the input values applied to the DUT during simulation.

Example:

```verilog
a = 4'b0011;
b = 4'b0101;
opcode = 2'b00;
```

This stimulus tells the ALU to perform ADD with inputs `3` and `5`.

In a testbench, stimulus is usually assigned inside an `initial` block or inside a `task`.

## Expected Result

Expected result

The expected result is the correct output that the testbench expects from the DUT.

Example:

```verilog
expected_result = 4'b1000;
expected_zero = 1'b0;
```

This means the testbench expects the ALU result to be `1000` and the zero flag to be `0`.

The expected result is not generated by the DUT.

It is written by the testbench writer and used as the reference answer.

## Actual Result

Actual result

The actual result is the output produced by the DUT.

For the ALU practice:

```verilog
result
zero
```

are actual outputs from the DUT.

The testbench compares these actual outputs with the expected outputs.

## PASS / FAIL Check

PASS / FAIL check

A better testbench should not only print signal values.

It should automatically compare the actual result with the expected result.

Example:

```verilog
if (result == expected_result && zero == expected_zero) begin
    $display("pass");
end else begin
    $display("fail");
end
```

This means the test case passes only when both conditions are true:

* `result == expected_result`
* `zero == expected_zero`

If either one is wrong, the test case fails.

## Task

Task

A `task` is used to organize repeated testbench code.

Instead of writing the same stimulus, delay, comparison, and display logic many times, I can put them into one reusable task.

Example:

```verilog
task run_test;
```

Then each test case can be written as one line:

```verilog
run_test("ADD", 4'b0011, 4'b0101, 2'b00, 4'b1000, 1'b0);
```

This makes the testbench cleaner, easier to read, and easier to extend.

## Task Input Parameters

Task input parameters

Task input parameters receive values from the task call by position.

Example:

```verilog
task run_test;
    input [79:0] test_name;
    input [3:0] test_a;
    input [3:0] test_b;
    input [1:0] test_opcode;
    input [3:0] exp_result;
    input exp_zero;
```

When calling:

```verilog
run_test("ADD", 4'b0011, 4'b0101, 2'b00, 4'b1000, 1'b0);
```

The values are matched by order:

| Position | Task Parameter | Value     |
| -------: | -------------- | --------- |
|        1 | `test_name`    | `"ADD"`   |
|        2 | `test_a`       | `4'b0011` |
|        3 | `test_b`       | `4'b0101` |
|        4 | `test_opcode`  | `2'b00`   |
|        5 | `exp_result`   | `4'b1000` |
|        6 | `exp_zero`     | `1'b0`    |

The names do not automatically match.

The order matters.

## Assigning Task Inputs to DUT Inputs

Assigning task inputs to DUT inputs

Task inputs are temporary parameters inside the task.

They are not automatically connected to the DUT.

Example:

```verilog
a = test_a;
b = test_b;
opcode = test_opcode;
```

This step sends the task input values to the actual testbench signals connected to the DUT.

Without these assignments, the DUT inputs would not change.

## `reg` and `wire` in Testbench

`reg`

A `reg` is used for signals assigned inside `initial`, `always`, or `task` blocks.

In the testbench, input stimulus signals are usually declared as `reg` because the testbench actively assigns values to them.

Example:

```verilog
reg [3:0] a;
reg [3:0] b;
reg [1:0] opcode;
```

`wire`

A `wire` is used for signals driven by another module or by continuous assignment.

In the testbench, DUT outputs are usually declared as `wire` because the testbench only observes them.

Example:

```verilog
wire [3:0] result;
wire zero;
```

The testbench does not assign values to `result` or `zero`.

The DUT drives them.

## `$display`

`$display`

`$display` prints information to the terminal during simulation.

It is useful for showing:

* test name
* input values
* actual output
* expected output
* PASS / FAIL result

Example:

```verilog
$display("pass | a=%b | b=%b | result=%b", a, b, result);
```

`$display` is only for simulation.

It does not describe hardware.

## `$dumpfile`

`$dumpfile`

`$dumpfile` specifies the VCD waveform file path.

Example:

```verilog
$dumpfile("04_testbench_practice/waves/alu_tb_refine.vcd");
```

This tells the simulator where to save the waveform data.

The path must be written as a string, so it must be inside double quotes.

## `$dumpvars`

`$dumpvars`

`$dumpvars` selects which signals should be recorded in the VCD waveform file.

Example:

```verilog
$dumpvars(0, alu_tb_refine);
```

This records the signals inside the `alu_tb_refine` module.

The module name is not written inside quotes because it is not a file path.

## `$finish`

`$finish`

`$finish` ends the simulation.

Example:

```verilog
$finish;
```

Without `$finish`, a simulation may continue running, especially if the testbench contains an `always` block such as a clock generator.

## `#10`

`#10`

`#10` means wait for 10 simulation time units.

If the file has:

```verilog
`timescale 1ns/1ps
```

then:

```text
#10 = 10 ns
```

In the refined testbench, the flow is:

```text
apply input stimulus
wait 10 ns
check actual output against expected output
print pass or fail
```

## `initial`

`initial`

An `initial` block runs once at the beginning of simulation.

It is commonly used in testbenches for:

* setting up waveform dumping
* applying test stimulus
* calling test tasks
* ending simulation with `$finish`

Example:

```verilog
initial begin
    run_test(...);
    run_test(...);
    $finish;
end
```

## `always`

`always`

An `always` block runs repeatedly or whenever its sensitivity list is triggered.

In source modules, `always @(*)` is commonly used for combinational logic.

In testbenches, `always` is often used to generate clocks.

Example:

```verilog
always begin
    #5 clk = ~clk;
end
```

For today's refined combinational testbenches, `initial` is enough because the test cases only need to run once.

## Why the Refined Testbench is Better

Original testbench

The original testbench only applied inputs and printed outputs or generated waveforms.

The user had to manually check whether the outputs were correct.

Refined testbench

The refined testbench includes expected values and automatic PASS / FAIL checks.

This makes the simulation more useful because the testbench can immediately identify whether the DUT behavior is correct.

## Today’s Refined Testbenches

MUX2TO1

The refined testbench checks whether `y` follows `a` when `sel = 0` and follows `b` when `sel = 1`.

Decoder2to4

The refined testbench checks all four input cases and verifies the one-hot output.

Full Adder

The refined testbench checks all eight combinations of `a`, `b`, and `cin`.

ALU

The refined testbench checks ADD, SUB, AND, OR, zero flag behavior, and 4-bit wraparound behavior.

## Common Problems and Fixes

Problem

The VCD file path caused an error.

Fix

The `$dumpfile` path must match the terminal working directory and must be written inside double quotes.

Problem

The testbench could not find a signal such as `test_opcode`.

Fix

The task input name and the name used inside the task must match exactly.

Problem

The result displayed only one bit.

Fix

The testbench signal width must match the DUT output width.

For example:

```verilog
wire [3:0] result;
```

is correct for a 4-bit ALU output.

Problem

The first line caused a syntax error.

Fix

The `timescale` directive must start with a backtick:

```verilog
`timescale 1ns/1ps
```

## Connection to VLSI / EDA / 3D IC

Verification is an essential part of digital IC design.

Writing RTL is not enough. The designer must also prove that the module behaves correctly under different input conditions.

In real VLSI and EDA workflows, verification helps catch functional bugs before synthesis, physical design, timing analysis, and layout implementation.

This practice builds the foundation for more advanced verification methods used in ASIC design and EDA flows.

## One Sentence Summary

A testbench is not hardware; it is a verification environment that drives inputs, checks outputs, reports PASS or FAIL, and generates waveforms for debugging.
